# Dual 设计开发计划

## 1. 项目目标

`Dual` 继续使用 Java 21 + Processing 开发。近期目标不是扩成大型游戏，而是把现有弓箭对抗做成一款可以重复游玩的完整创意小游戏：规则易懂、对抗可读、单场紧凑，并同时支持人机、本地双人和联机双人。

产品规则与取舍以 [游戏设计](GAME_DESIGN.md) 为准，具体实现边界以 [玩法落地开发指导](GAMEPLAY_IMPLEMENTATION_GUIDE.md) 为准，工程边界以 [技术路线说明](TECHNOLOGY_EVALUATION.md) 为准。

当前仓库的 Rust + Macroquad 并行迁移不改变 Java 基线里程碑。迁移阶段、接口边界、提交顺序和 Windows 无 JVM 验收条件见 [Macroquad 迁移计划](01-macroquad-migration-plan.md)。

## 2. 当前基线

### 已有能力

- 默认铺满 1920 x 1080 窗口的 16:9 游戏区域，以及 1280 x 720 确定性竞技场和几何视觉风格。
- 玩家移动、边界反弹、短弓、长弓蓄力和箭矢碰撞。
- 短弓命中后的击退与暂时失控，长弓命中后的立即击杀。
- AI 演示、人机对局和 TCP 联机输入转发。
- 粒子、屏幕震动、倒计时、暂停和基础操作说明。
- JUnit 规则测试、Gradle 构建和 Windows `jpackage` 打包。

### 主要缺口

- 标准比赛代码已具备回合比分、整场胜负和快速再战；仍需完成十场桌面试玩后才能关闭 R1 验收门槛。
- 回合结果反馈仍需桌面验证；破绽倒计时环、长弓完成反馈、拦截停顿、短弓恢复条和本地回合战斗报告已加入。
- 短弓储备、逐支恢复和连续破绽刷新上限已实现，AI 已复用同一资源规则；尚未完成十场真人对局数据验证。
- 已有同键盘本地双人模式、独立键位、玩家二键盘瞄准和完整比赛流程测试；尚未完成本地双人桌面试玩。
- 战斗规则、场景表现和模式入口仍较紧密，增加回合规则容易产生重复状态。
- Relay 目前转发输入、回合结果和再战请求；客户端仍需通过确定性规则与结果一致性门禁防止双端比分分歧。

## 3. 开发原则

- 每次只交付一个可测试的小功能，并在验证通过后独立提交。
- 先抽出当前功能需要的纯规则，不进行脱离需求的大规模重构。
- 所有比赛规则使用帧数或确定性输入推进；联机战斗不得依赖未同步的系统时间或随机数。
- AI、人类和网络玩家只提供输入，不能分别拥有不同的伤害、冷却或胜负逻辑。
- 修改非平凡函数时添加面向初学者的简短注释，说明职责、输入输出和关键副作用。
- 每个里程碑完成后进行桌面试玩；自动化测试通过不等于玩法已经成立。

## 5. 近期实施顺序

### 阶段记录：D4 战术事件与反馈（已完成）

D4 的目标是让玩家能看懂“短弓制造机会、长弓兑现机会”的过程。它只记录已经发生的战斗事实并提供反馈，不增加伤害倍率、额外控制时间或隐藏命中修正。自动瞄准范围、短弓三发储备和现有武器数值在本阶段保持不变。

#### D4.1 纯战术事件记录器

- 定义 `PRESSURE`：攻击者的短弓命中目标并造成击退的事实。
- 定义 `OPENING`：目标仍处于本次 `PRESSURE` 的有效窗口时，同一攻击者开始长弓蓄力的事实。
- 定义 `FINISH`：同一攻击者的长弓在该事件链有效期间击杀目标的事实。
- 记录器只保存玩家标识、事件类型和战斗帧号，不持有 `App`、Processing 绘制对象、玩家或箭矢引用。
- 第一版破绽窗口固定为 90 帧；该窗口只决定反馈事件能否串联，不改变受击、移动、蓄力和死亡规则。

验收：JUnit 覆盖正常事件链、超时、双方事件隔离、顺序错误、重复命中和回合重置。记录器对相同输入必须产生相同结果。

提交边界：纯事件类型、记录器和规则测试组成一个提交，不包含视觉效果。

#### D4.2 战斗碰撞接入

- 短弓实际命中并执行击退后提交 `PRESSURE`。
- 玩家从非长弓状态进入长弓蓄力时提交“开始蓄力”事实；记录器自行判断是否形成 `OPENING`。
- 提前释放或受击打断会撤销当前蓄力对应的 `OPENING`；短弓打断另外提交独立的 `DISRUPT` 事实。
- 长弓实际击杀后提交终结事实；只有满足完整事件链时生成 `FINISH`。
- 箭矢相撞提交独立的 `INTERCEPT` 事实，用于反馈，但不属于三段战术连击。
- 每轮开始或单局重置时清空未完成事件链，不能把上一轮的 `PRESSURE` 带入下一轮。

验收：状态机与碰撞测试证明每次实际行为只提交一次事件；未命中、被拦截、取消蓄力和超时均不得产生错误的 `FINISH`。

提交边界：碰撞与状态机接入及其测试组成一个提交，不改变现有粒子和 HUD。

#### D4.3 屏幕反馈

- `PRESSURE`：受击目标周围出现短促的中性破绽环。
- `OPENING`：攻击者开始有效长弓蓄力时，锁定环切换为醒目的机会状态。
- `DISRUPT`：打断者显示 `CHARGE BREAK`，目标处出现琥珀破裂环和短促命中停顿。
- `FINISH`：沿用致命轨迹，并短暂显示完整事件链结果。
- `INTERCEPT`：箭矢交点使用区别于角色受击的碎裂效果。
- 结算页并列显示双方命中/发射与蓄力打断，并汇总中立的箭矢拦截和有效战斗时长，为十轮试玩提供统一记录口径。
- 所有反馈必须使用固定画布坐标或明确跟随的世界坐标；文本与 HUD 不随屏幕震动漂移。

验收：在 1280 x 720 内部画布、1920 x 1080 默认窗口和非 16:9 窗口各走查一次；反馈不能遮蔽角色、弹药 HUD或长弓蓄力环。

提交边界：每一种反馈单独提交；如果试玩无法说明该反馈的含义，则回退该反馈提交，不回退已验证的事件记录器。

#### D4.4 完成门槛

- 完成至少十轮人机试玩，逐轮记录是否出现 `PRESSURE`、`OPENING`、`DISRUPT`、`FINISH` 和 `INTERCEPT`。
- 试玩后玩家能够准确说明短弓命中是否创造了机会、机会何时失效，以及长弓为什么构成或不构成终结。
- 自动化测试、`gradlew build` 和 `git diff --check` 全部通过。
- D4 完成前不进入先胜三回合、中央掩体或联机协议扩展。

D4 完成后的历史顺序是 R1.1 纯比赛规则；当前实施顺序以 R7.4 联机输入闭环为准。

### R0：基线与方向

1. 建立游戏设计文档，定义术语、标准比赛和内容边界。
2. 将开发计划改为按可玩结果验收的小里程碑。
3. 运行 `gradlew test`、Markdown 链接检查和 `git diff --check`。

完成后只继续 R1，不并行加入场地、武器或联网协议。

### R1：输入与标准比赛

R1 的第一优先级是先解决人类操作负担，再实现回合结构。输入目标为 `WASD` 移动 + 鼠标瞄准 + 鼠标左键短弓 + 鼠标右键长弓；键盘兼容方案保留。具体 D1-D6 交付顺序和验收见 [玩法落地开发指导](GAMEPLAY_IMPLEMENTATION_GUIDE.md)。

#### R1.1 纯比赛规则

- 新增不依赖 Processing 绘制的比赛计分类，维护双方比分、先胜目标和比赛是否结束。
- 明确定义“本回合胜者”和“整场胜者”，避免复用含糊的 `win/lose` 布尔值。
- 测试零比分、双方得分、先胜三回合、比赛结束后拒绝重复计分。

验证：目标 JUnit 测试、完整 `gradlew test`、`git diff --check`。

#### R1.2 回合重置

- 将玩家出生、速度、状态、箭矢和临时粒子重置为新回合基线。
- 保留比赛比分、当前模式和有效网络连接。
- 测试回合重置不会残留死亡角色、箭矢、破绽或蓄力状态。

验证：规则测试加人机连续两回合桌面冒烟。

#### R1.3 比分 HUD 与结果状态

- 顶部显示比分、当前回合和先胜目标。
- 区分“本回合获胜”和“整场比赛获胜”。
- 最终结果提供再战与返回入口，不自动强制回到演示模式。

验证：场景运行走查常见窗口比例，并检查文本不遮挡战斗区域。

#### R1.4 人机完整比赛

- 启动后可从演示进入标准人机比赛。
- 完成先胜三回合后可以使用相同模式立即再战。
- 记录十场对局的回合时长与异常状态，修复阻断问题后再结束 R1。

验证：`gradlew test`、`gradlew build`、桌面完整比赛试玩。

### R5：AI 打磨

- R5.1-R5.4 已加入 Basic、Standard、Advanced 三档配置，分别调整反应周期、决策概率、长弓释放时机、Advanced 假蓄力和拦截瞄准；尚未通过桌面试玩验证学习曲线。
- 基础 AI：明显蓄力预警、较慢反应，教会玩家短弓与长弓关系。
- 标准 AI：会规避近距离箭矢、在破绽期间尝试长弓击杀。
- 进阶 AI：会假蓄力、选择拦截时机和控制短弓资源，但不能读取玩家未来输入或修改物理规则。

三档 AI 使用同一决策框架和规则参数；难度只调整反应窗口、决策概率和允许使用的策略。

### R7：联机整合

#### R7.1 回合结果协议状态

- 客户端与 Relay 共享 `TYPE_ROUND_RESULT` 固定长度帧，显式携带回合序号、胜者、双方比分和比赛完成标记。
- 客户端在收到结果时按回合序号去重，旧帧和重复帧不会覆盖最新状态；发送端在本地回合结算后发送自己的结果快照。
- 已覆盖客户端编解码、接收去重、Relay 原样转发、直连握手和断线边界测试。
- 直连集成测试已在同一 TCP 连接上完成两场结果同步，并验证中间的整场再战请求。
- Relay 集成测试已在同一 Relay 连接上转发两场结果和两次再战请求。

验证：客户端网络测试、Relay 测试和标准比赛回归通过；仍需双客户端完成比分镜像、再战握手和延迟试玩。

#### R7.2 再战请求握手

- 结算层发送带回合号的 `TYPE_REMATCH_REQUEST`，普通回合和比赛结束使用同一帧区分。
- 联机状态机只有在收到对端同回合、同类型请求后才重置；旧回合请求不会触发新回合，等待期间保留结算画面。
- 等待对端请求最多持续 5 秒；超时保留结算画面并提示释放 `X` 重试，不会单端强行进入下一回合。
- 已覆盖请求编解码、接收去重、Relay 原样转发和旧请求边界测试。
- 已覆盖同一连接完成整场再战后清空远端快照，并从下一场的回合 1 重新同步。

验证：客户端与 Relay 协议测试、标准比赛回归通过；仍需两端实际延迟和断线再战试玩。

#### R7.3 比分一致性门禁

- 本地结算前必须收到对端同一回合的结果帧，并将对端视角镜像后与本地胜者、双方比分和比赛完成标志逐项比较。
- 结果帧缺失时继续等待；结果帧存在但不一致时显示比分分歧提示，不允许再战请求推进状态。
- 已覆盖匹配结果、延迟结果和分歧结果的规则测试。

验证：GameSystem 网络一致性测试、直连集成冒烟和完整客户端/Relay 构建通过；仍需直连与 Relay 的实际多场比赛。

#### R7.4 联机手动瞄准同步

- `TYPE_INPUT` 固定为 4 字节，沿用 6 个移动/武器 flags，新增 `HAS_AIM` 位和量化的绝对 `aimAngle`。
- 客户端在固定 1280 x 720 竞技场坐标中发送最近有效鼠标或键盘瞄准角；画布外或无瞄准输入不会覆盖此前有效角度。
- 远端玩家按上下镜像恢复角度，再由同一长弓状态机决定自动锁定、掩体遮挡和手动预瞄；不改变武器、碰撞、比分或回合规则。
- Relay 只按固定长度原样转发输入帧；非法 flags、截断帧和不匹配的旧输入帧不会继续驱动比赛。

验证：角度量化、客户端接收线程、直连和 Relay 输入转发测试通过；仍需两端在开放场远距和中央掩体场完成手动瞄准试玩。

1. 明确回合开始、回合结果、比赛结果和再战所需的协议状态。
2. 优先通过确定性输入复用本地规则；无法可靠推导的状态必须显式同步。
3. 增加比分分歧、重复结果、断线和再战超时测试。
4. 使用直连和 Relay 各完成多场标准比赛。

任何会改变联机报文格式的提交都必须同时更新客户端、Relay、协议测试和 README。

## 7. 每个功能的完成定义

一个功能只有同时满足以下条件才算完成：

1. 行为与本计划或游戏设计中的术语一致。
2. 非平凡规则具有初学者可读的函数级注释。
3. 风险对应的自动化测试或人工验证已经通过。
4. `git diff --check` 通过，改动中没有无关文件。
5. README 或设计文档在玩家可见行为变化时同步更新。
6. 作为一个独立提交落地，提交信息描述实际完成的功能。

## 8. 暂停条件

- 若玩家无法解释死亡原因，暂停新增内容，先修战斗反馈。
- 若短弓持续按键始终优于观察和预判，暂停场地开发，先完成 R3。
- 若比赛频繁超过五分钟或单回合超过 60 秒，先验证决胜阶段，不增加随机事件。
- 若新场地让某一出生方向拥有稳定优势，停止增加场地并修正镜像与碰撞。
- 若联机双方可能得到不同比分，停止联机功能扩展，先建立可复现的分歧测试。
- 若新增系统不能改变位置、时机、风险或反制选择，则不进入近期开发计划。
